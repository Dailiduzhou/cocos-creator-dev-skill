# Script basics (Creator 3.8 baseline)

## Project setup

Create component scripts under `assets/`, normally through the editor. Preserve the accompanying `.meta` file when moving/renaming assets so serialized references retain their UUIDs. Keep existing class names and serialized property names unless migration is intentional.

Use TypeScript for components and ESM imports from `cc`. Creator also supports JavaScript modules and plugin scripts; support for third-party packages depends on their module format and platform APIs. A Node.js library is not automatically compatible with a browser or native game runtime.

### TypeScript configuration

Keep the root `tsconfig.json` extending **the file generated by the installed Creator version**. Inspect the actual project rather than hardcoding a generated path: documentation and editor releases can differ (`temp`/`tmp`). Do not edit generated config files.

Add desired checking options to the existing `compilerOptions`, for example `noImplicitAny`, only with regard to the project's existing code. Do not replace `target` or `module`: the official manual warns that these do not control Creator's compilation as they would in a standalone `tsc` build and can make IDE checks disagree with runtime behavior.

Use the existing project type-check command if provided. A passing editor import is not necessarily a full TypeScript type check, and `tsc` alone does not validate scene wiring or platform execution.

## Minimal component with explicit Inspector types

```typescript
import { _decorator, Component, Enum, Node, isValid } from 'cc';
const { ccclass, property } = _decorator;

enum Direction { Left, Right }
Enum(Direction);

@ccclass('Mover')
export class Mover extends Component {
    @property(Node)
    target: Node | null = null;

    @property({ min: 0, tooltip: 'Local units per second' })
    speed = 10;

    @property({ type: Direction })
    direction: Direction = Direction.Right;

    @property([Node])
    waypoints: Node[] = [];

    update(dt: number): void {
        const target = this.target;
        if (!target || !isValid(target, true)) return;
        const p = target.position;
        const sign = this.direction === Direction.Right ? 1 : -1;
        target.setPosition(p.x + sign * this.speed * dt, p.y, p.z);
    }
}
```

Attach `Mover` to a node and drag the desired target node into `target` in the Inspector. If the target is intentionally the same node, using `this.node` avoids an unnecessary serialized reference.

## Decorators and serialization

- `@ccclass('Name')`: use a project-wide unique name. Components need this registration for editor attachment and serialization.
- `@property(Node)` / `@property(Sprite)` / `@property(Prefab)`: explicit runtime types let the editor serialize object references. TypeScript type annotations alone are insufficient.
- Primitives need no type: `@property label = ''` already serializes as `CCString`, and `type: String`/`Number`/`Boolean` triggers the manual's warning against the constructors while adding nothing. Use `CCString`/`CCFloat` only as array element types such as `[CCString]`.
- `@property([Node])`: specify array element types; empty arrays do not provide useful inference.
- Register enum values with `Enum(...)` and supply the enum as the property type.
- `@requireComponent(Sprite)`: declares a required component on the same node. Import/destructure it from `_decorator`.
- `@executionOrder(-10)`: controls supported lifecycle execution order; a field named `executionOrder` does not.
- `@executeInEditMode(true)`: deliberately enables editor-time behavior. Avoid runtime side effects such as network calls or destructive scene edits during authoring.
- `@property({ serializable: false })` excludes persisted state. TypeScript `private` is not a substitute for serialization settings.

Avoid assigning `null` to a non-nullable type just to copy an old example. `Node | null = null` honestly represents an unwired property; a non-null assertion does not validate Inspector setup.

## Dependencies and modules

Prefer class-based `getComponent(MyComponent)` and typed serialized references. Check lookup results before use. Use `import type` for type-only dependencies; avoid circular module initialization, especially global singletons constructed at import time.

For inheritance, explicitly call `super` when a subclass lifecycle callback must retain base-class work. Keep class construction free of assumptions about serialized properties or scene state; initialize those in lifecycle methods.
